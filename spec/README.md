# Substrate executable specification

The first ESS projection describes the **accepted-operation ledger** implemented by the SQLite
store. It is derived from shipped code; it neither changes the runtime nor replaces the immutable
wire bundles. Read [coverage and limitations](coverage.md) before interpreting a green result.

The exact CLI pin is in `ess-inputs.yaml`: ESS 0.77.0. Install that official release, or use
`ess specify toolchain install 0.77.0` with an existing ESS CLI. CI installs its checksum-verified
Linux archive. There is no ESS implementation dependency in the Substrate workspace.

```console
ess specify validate --path spec
ess specify compile --path spec --format json
ess verify conform synthesize --path spec --out spec/operations-suite.json
cargo xtask check-ess
cargo test --locked -p b10x-substrate-store --test ess_operations -- --nocapture
```

`cargo xtask check-ess` regenerates into a temporary directory and compares exact bytes with the
committed suite. The full gate executes all 14 scenarios against the production `Store`, reading
persisted rows and events. The Rust adapter fails on an unknown command, step, expression or event,
and pins the scenario count so a changed inventory requires review. It does not execute the ESS
reference implementation or infer observations from the expected outcome.

`task check` runs the complete existing repository gate, including ESS and public documentation.

The `b10x-substrate` client CLI has its own projection in [`client/`](client/README.md): a
presentation domain and an `ess-cli/2` binding, whose generated contract package is committed in
`generated/cli` and drift-checked by `cargo xtask check-ess`. It runs no conformance suite.

The workspace projection in [`workspaces/`](workspaces/README.md) (ADR 0035) models the root-name
set, the workspace origin, `workspace.adopt` and `workspace.destroy`. `cargo xtask check-ess`
validates it, holds `workspaces-suite.json` to its regenerated bytes, runs that suite against the
ESS `interpreted` reference (a model check, not daemon conformance), and holds
`crates/substrate-wire/src/generated/workspace.rs` (`RootName`, `WorkspaceOrigin`) to its
regenerated bytes.

The host-process resource family of ADR 0036 is specified in [`host-processes/`](host-processes/README.md)
(domain `substrate.host_processes`). `cargo xtask check-ess` validates it, compares its committed
synthesized suite `host-processes-suite.json` byte for byte, and runs the synthesized and authored
scenarios against the ESS interpreted reference, which checks the model and not the daemon.

The confinement contract of ADR 0044 (atlas ADR 0109) is specified in
[`confinement/`](confinement/README.md) (domain `substrate.confinement`). It pins ESS 0.77.0 in its
own `ess-inputs.yaml`. `cargo xtask check-ess` validates it, holds `confinement-suite.json` to its
regenerated bytes, runs that suite against the ESS `interpreted` reference, and holds
`crates/substrate-host/src/generated/confinement.rs` (`ContractFamily`, `AdapterName`, `Fact`) to
its regenerated bytes. The interpreted run checks the model, not an adapter. Each adapter's lane
runs the authored scenarios named for it against that adapter; synthesized scenarios name no
adapter or lane and run against the interpreted reference only.
